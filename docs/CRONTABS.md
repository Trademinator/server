# Trademinator cron configuration

This is the canonical list of operating-system cron entries required by Trademinator. Update this file whenever a scheduled Artisan command is added, removed, renamed, or its cadence changes, and whenever queue processing requirements change.

Trademinator is designed to run without a permanent daemon. The managed queue deployment uses shared Redis and drains it from cron with `trademinator:queue-work --stop-when-empty`. Each invocation supervises a finite Laravel worker and sends independent heartbeats while that child executes jobs.

## Required crontab entries

The owner/observability update adds `trademinator:prune-access-statistics` to the existing Laravel scheduler at **02:40 daily** (application timezone), with `onOneServer()` and a 60-minute overlap lock. Keep the scheduler cron below; no new application daemon or queue is required. `ACCESS_STATISTICS_RETENTION_DAYS` defaults to 90 and removes expired aggregates and daily visitor hashes, while preserving today and the preceding N−1 UTC dates. See [owner, syslog and GeoIP setup](CLI.md#owner-administration-syslog-and-local-geoip).

Action syslog is generated by the application independently of cron's stdout/stderr redirection. Verify it with `journalctl -t trademinator -f -o cat` on each worker/web host. Keep the existing cron log redirections for boot errors and command output. Ensure the PHP process/chroot can reach the local syslog socket and configure OS retention/rate limits for the event volume.

For a local MaxMind City database, use the operating system's `geoipupdate` timer or an operator-managed cron entry such as the following, **only after** configuring its private account/license settings and installing the utility:

```cron
17 2 * * * root /usr/bin/geoipupdate
```

Run this as the account authorized to read `/etc/GeoIP.conf` and replace the configured City MMDB. No credentials appear on the command line. Use the actual binary/database paths for your distribution. Keep `GEOIP_DATABASE_PATH` consistent with that location and readable by the application on each node. The application performs only local MMDB lookups; it never downloads a database itself or sends visitor IPs to an external service. Database updates do not need an application restart because each lookup opens the current file.

Replace `/path/to/trader-server` and `/usr/bin/php` with the deployment's actual paths.

All cron examples use **`/etc/cron.d/trademinator`**, with the application account (`apache` below) after the five schedule fields. Adjust the account and paths for the deployment. Run workers as the account that owns the application's writable storage.

```cron
# Laravel scheduler. This triggers all schedules defined in routes/console.php.
* * * * * apache cd /path/to/trader-server && /usr/bin/php -d memory_limit=512M artisan schedule:run >> storage/logs/scheduler-cron.log 2>&1

# One Redis-owned slot per host and queue pool; the next minute skips an occupied slot.
* * * * * apache cd /path/to/trader-server && /usr/bin/php -d memory_limit=512M artisan trademinator:queue-work redis --queue=default --slot=1 --stop-when-empty --max-time=50 --memory=384 --timeout=600 --tries=5 >> storage/logs/queue-cron.log 2>&1

# Dedicated feature capacity keeps live features moving while training is busy.
* * * * * apache cd /path/to/trader-server && /usr/bin/php -d memory_limit=512M artisan trademinator:queue-work redis --queue=features --slot=1 --stop-when-empty --max-time=50 --memory=384 --timeout=600 --tries=5 >> storage/logs/features-cron.log 2>&1
```

These entries cover the scheduler, collection and M2 features. M4 training also requires the intelligence queue worker below, and signal recording requires its own signals worker. Historical backfill uses the additional history worker below. Match queue names to configuration, including `FEATURES_QUEUE`. Do **not** add separate cron lines for each scheduled application command; Laravel's scheduler owns those cadences.

## Queue and cache requirements

Use `QUEUE_CONNECTION=redis` and a shared Redis cache for managed workers and queue controls. Every node must use the same Redis namespace, database, source version, application database and shared private model/research storage. Set `WORKER_REDIS_CONNECTION` to the Redis database connection used by the queue (normally `default`), not the Laravel queue connection name. A connection consumed by training must reserve jobs for at least the derived whole-build timeout plus **300 seconds**. This timeout covers every enabled algorithm and parameter run, so it can be much longer than `INTELLIGENCE_MAX_SECONDS`. The separate `redis-signals` queue connection reserves jobs for **1200 seconds**, above its recorder's **900-second** timeout.

Composer requires `ext-pcntl`. Install and enable PCNTL for the same PHP CLI binary used by cron and Composer; Laravel's hard worker timeouts depend on it. A CLI worker with a different PHP configuration must also load the extension.

Use a shared atomic-lock-capable cache store such as Redis when multiple application nodes run the scheduler. `onOneServer`, `withoutOverlapping`, database leases, and per-market locks protect shared work from duplicate execution. The every-minute market-feed dispatcher uses a five-minute scheduler overlap expiry to suppress redundant dispatcher runs; its atomic 15-minute database feed lease remains the correctness boundary if that scheduler lock expires. The R3 exchange refresh runs on **every node** because each node owns its installed CCXT files and runtime snapshot; the command uses its own local file lock and a shared cache lock for database inserts. It is offline and does not update the CCXT package or approve changed adapters. Composer install/update also rebuilds local metadata without database access. No additional system cron entry is needed.

Worker cron entries use an ownership-checked Redis slot lease instead of `flock`. The key contains the hostname and IP, queue pool and slot. The worker ID also contains the supervisor PID and a fresh UUID. Set `WORKER_HOSTNAME` and `WORKER_IP` explicitly in containers or on multihomed machines; otherwise the hostname and its resolved address are used. Each host may use slot `1`; add a second cron entry with `--slot=2` to permit a second simultaneous worker in the same pool. Plan CPU/RAM capacity before increasing slots. Domain locks for markets, exchanges and model publication stay shared across hosts.

### Worker heartbeat and lost contact

The supervisor renews its owned slot and records child process liveness independently of application progress. Defaults are `WORKER_HEARTBEAT_SECONDS=10`, `WORKER_OVERDUE_SECONDS=30`, `WORKER_LOST_SECONDS=60`, and `WORKER_LEASE_SECONDS=90`; configure them in that increasing order. `WORKER_RETENTION_SECONDS=604800` retains last-known records for seven days. The Owner queue page shows the host, IP, PID, active job, heartbeat and progress separately. A healthy heartbeat does not prove that an algorithm is making progress.

Contact loss does not cancel a job, clear a domain lock or requeue a reservation. A supervisor that loses slot ownership requests that its child stop taking work and waits for the child to exit. A child checks its supervisor and slot before new claims; training checkpoints and publication guards also reject a lost supervisor or lease. A blocked native call cannot check until it returns, so its reservation and domain locks remain in place. The supervisor itself does not use the job's alarm timer. Job timeouts, domain leases and queue `retry_after` remain independent of worker presence.

A slot lease is an ownership guard, not proof that a missing process has exited. After its lease expires, a replacement may start while an orphan finishes work without checkpoints; this can temporarily exceed that slot's intended CPU/RAM concurrency. Shared resource locks and reservations still protect the existing work. Investigate lost contact on the affected host before assuming its resources are free.

When deploying this change, stop the old `flock` workers and replace their cron entries before enabling managed slots. Do not leave old and new worker launchers running together. The managed launcher passes the parent's loaded PHP configuration and `-d memory_limit` to its child; the scheduler's existing command wrapper does the same for scheduled commands.

## Bounded queue memory and worker recycling

PHP's `-d memory_limit` is the hard ceiling **during a job**. The managed command passes `--memory` to Laravel's worker, which checks that recycle threshold **between jobs**. Set both explicitly as in the commands above/below. The worker threshold deliberately leaves room below PHP's ceiling. `--max-time=50` returns control to cron between jobs and allows a running job to finish. The supervisor continues its heartbeat for the child's full lifetime, including a long training job.

Candle workers install only the requested instrument into CCXT's market indexes, disable retained response copies, and reuse unchanged adapter settings. Binance spot metadata is normalized one instrument at a time without building all derivative/currency indexes. Other adapters may still require a complete metadata response from their API; OHLCV ingestion remains paged. Replaced SDK objects and unused allocator pages are reclaimed between jobs on every queue.

| Queue | Bounded work |
| --- | --- |
| `default` | Live ingestion uses a 90-period window; period selection uses the recent 250-candle sample plus boundary allowance. Explicit queued synchronization processes one configured page per job and preserves its queue/connection on continuation. |
| `features` | Feature replay streams 500 source candles at a time and writes batches of 100, retaining only indicator state and a 30-day close-price buffer. |
| `history` | At most five 90-candle requests per pass, with transactional progress checkpoints and the existing 45-second work budget. |
| `intelligence` | Feature replay uses the same streaming path. Training and retained KNN knowledge use every eligible example within `INTELLIGENCE_MAX_MODEL_AGE_DAYS` of the build cutoff; there is no row-count cap. Longer windows increase model memory and fitting time; application and worker time budgets still apply. Human-review snapshots and their chart payloads are read 25 at a time. |
| `signals` | One pending recorder per actively subscribed market loads its model and recent feature window, then processes up to six new completed source candles. Its worker runs independently of training. |

After deploying these changes, update the configured queue cron commands and add the dedicated signals worker. Inspect `php artisan queue:failed` and the corresponding worker log if a job fails. Keep ingestion batches bounded and size the intelligence age window and worker resources together. These budgets are not a benchmark of every exchange adapter or a guarantee about production RSS.

## Deployment checks

After changing application or environment configuration:

```bash
php artisan config:clear
php artisan config:cache
php artisan schedule:list
php artisan queue:failed
```

Use targeted `config:clear` / `config:cache` during this rollout. `optimize:clear` also clears application cache and can erase the uniqueness and recovery locks that protect pending jobs; `cache:clear` has the same lock risk. New cron workers load the refreshed code and configuration, while a worker already running retains its loaded version until it exits. Stop intelligence and signals workers on every host before applying the [targeted legacy backlog recovery](CLI.md#trademinatorrecover-signal-queue).

The historical single-host helper, `scripts/repair-signal-pipeline.sh`, belongs to the earlier pinned signal repair. It generates legacy `flock` workers and does not recognize the managed supervisor/child commands. **Do not use it for this managed-worker rollout or on a managed cluster.** Update `/etc/cron.d/trademinator` using the commands in this document, stop the old consumers on every host, refresh configuration, and use the manual recovery procedure when a legacy mixed backlog needs repair. If lost-contact workers remain in the registry, verify their processes have exited before adding `--workers-stopped`; this acknowledges and removes their stale active-registry entries while retaining available last-known metadata.

## M4 intelligence workers

M4 adds a dedicated CPU-heavy queue. Keep the scheduler on one or multiple scheduler nodes and drain `intelligence` on a worker machine with the same source, database, shared cache and shared private model/research storage. Web nodes do not need to drain this queue. No permanent daemon is required.

```cron
# Add on each chosen intelligence worker, alongside or instead of that node's default-queue worker.
* * * * * apache cd /path/to/trader-server && /usr/bin/php -d memory_limit=512M artisan trademinator:queue-work redis --queue=intelligence --slot=1 --stop-when-empty --max-time=50 --timeout=2400 --memory=384 --tries=3 >> storage/logs/intelligence-cron.log 2>&1
```

`INTELLIGENCE_QUEUE` defaults to `intelligence`; if changed, change the worker's `--queue` to match. Worker PHP needs the same Composer extensions as the application, including PCNTL. Memory needs depend on schema/history; 512 MiB is a starting limit, not a production benchmark. Recovery acquires a shared maintenance guard and requires affected consumers on every host to be stopped. Its legacy local lock checks remain for older launchers. A stale heartbeat alone does not prove that an old child exited; use `--workers-stopped` only after verifying all affected processes on every host have exited. The option never bypasses a live slot lease.

Weekly dispatch runs Monday at 04:00 in the application timezone using shared scheduler locks. Per-market uniqueness/build locks and the database's unique weekly generation key also protect redelivery after a worker crash. Retries use 300/900-second backoff. Completed generations include abstaining models; failed input/history builds remain visible in normal failed-job reporting. Training snapshots/models are retained for audit and need ordinary backup/storage capacity planning.

The intelligence page shows this next dispatch time in UTC, separately from its conditional data-collection ETA. The displayed schedule does not verify that the scheduler or worker is running. If a weekly model has already completed but is abstaining, newly collected history will be evaluated at the next weekly run; use a direct `trademinator:knn-build` to reevaluate sooner. See [intelligence readiness](CLI.md#reading-intelligence-readiness) for the row targets and validation checks.

Set `INTELLIGENCE_ENABLED=false` to disable weekly dispatch. To populate initial models, after M2 features exist, run:

```bash
php artisan trademinator:dispatch-market-intelligence
php -d memory_limit=512M artisan trademinator:queue-work redis --queue=intelligence --slot=1 --stop-when-empty --max-time=50 --timeout=2400 --memory=384 --tries=3
php artisan queue:failed
php artisan schedule:list
```

`INTELLIGENCE_MAX_SECONDS` is the cooperative time allowance for **one algorithm and parameter run**, in seconds (default **1800**). Outcome and Action K selection give each K its own allowance across all folds and rows. Shared preparation and neighbor-search time is charged to every K; time spent scoring a different K does not consume its allowance. Each fixed-K holdout, ablation, pattern learner, lead/lag parameter run, Human Training policy, and enabled CoinGecko learner starts a fresh allowance. Preparation stages are separately bounded. Dataset construction retains its own `RESEARCH_DATASET_MAX_SECONDS` limit. An explicit audit/caller deadline remains an overall cap.

The hard job timeout is calculated from all possible enabled runs, dataset construction, and cleanup time. `INTELLIGENCE_JOB_TIMEOUT` can raise that calculated minimum; `0` means use the calculation. Each training job carries this timeout, which takes precedence over the worker's `--timeout=2400` fallback. The worker cron does not need a new `--timeout` each time the algorithm allowance changes. Database/Redis/Beanstalkd configuration enforces `retry_after >= job timeout + 300`, preserving any larger configured value. Configure SQS visibility separately to satisfy the same reservation margin.

Training cache locks and running database leases use renewable ownership-checked leases. Their duration covers the longest single algorithm, dataset, or feature-replay stage plus cleanup time; progress checkpoints renew them while work is running. They do not retain the potentially very long whole-build reservation after a process dies. Loss of ownership aborts publication. Queue reservations still cover the whole build, so a crashed queued build can need the existing targeted recovery procedure before that reservation expires.

For a **24-hour allowance per run**, use:

```dotenv
QUEUE_CONNECTION=redis
INTELLIGENCE_MAX_SECONDS=86400
INTELLIGENCE_JOB_TIMEOUT=0
REDIS_QUEUE_RETRY_AFTER=0
INTELLIGENCE_SIGNALS_QUEUE=signals
INTELLIGENCE_SIGNALS_CONNECTION=redis-signals
REDIS_SIGNALS_RETRY_AFTER=1200
```

The `0` queue setting above selects the application's calculated floor; it does not disable the reservation. A complete build may take more than 24 hours because its runs have independent allowances. Inspect effective values after loading configuration:

```bash
php artisan tinker --execute='dump(App\Domain\Intelligence\TrainingRuntime::jobTimeout(), App\Domain\Intelligence\TrainingRuntime::lockSeconds(), App\Domain\Intelligence\TrainingRuntime::retryAfter());'
```

Refresh configuration with `config:clear` followed by `config:cache`, then run `queue:restart` so workers reload it. Already queued payloads retain their serialized timeout; restarting workers alone does not update them. With the consumers stopped as required by its safety checks, the targeted recovery command refreshes retained training payloads while preserving their work. Newly dispatched jobs use the current budget. Existing published models remain unchanged until rebuilt. Keep the signals worker at **900 seconds**, independently of the training allowance.

With `ACTION_SYSLOG_ENABLED=true`, watch the existing structured action log:

```bash
journalctl -t trademinator -f -o cat | grep --line-buffered -E 'intelligence\.human_training\.|job\.timeout|intelligence\.build\.completed'
```

Replace `trademinator` with `ACTION_SYSLOG_IDENT` if customized. Human-training events include `started`, `progress`, `completed`, `timeout`, `failed` and `skipped`. They identify the exchange, symbol, period, dataset, current stage, elapsed/remaining milliseconds, configured budget, memory and available row/progress counts. Stage changes log immediately; continuing loops log at most once every ten seconds. A blocked database/filesystem call cannot emit progress while blocked: the last stage identifies where it stopped, and the worker's existing `job.timeout` event records a hard timeout. `completed` also records the validation status; it does not necessarily mean the model passed validation.

M4 does not change the default queue timeout or M1/M2 collection cadences. `derive-timeframe`, direct `knn-build`, `model-info` and `signal` are on-demand commands. Longer derived timeframes are not automatically retrained by the base-period dispatcher. See [the complete CLI workflow and model contracts](CLI.md#m4-intelligence-workflow-and-upgrade).

## Historical OHLCV backfill worker

Apply the migration and refresh deployment configuration before enabling the updated scheduler:

```bash
php artisan migrate --force
php artisan config:cache
php artisan schedule:list
```

`HISTORY_BACKFILL_ENABLED` defaults to `true`; `HISTORY_BACKFILL_QUEUE` defaults to `history`. Keep the existing scheduler, default-queue, intelligence-queue and signals-queue crons. Add this entry on the chosen history worker machine(s), using the same source, database and shared cache:

```cron
* * * * * apache cd /path/to/trader-server && /usr/bin/php -d memory_limit=512M artisan trademinator:queue-work redis --queue=history --slot=1 --stop-when-empty --max-time=50 --timeout=120 --memory=384 --tries=1 >> storage/logs/history-cron.log 2>&1
```

Change `--queue` to match `HISTORY_BACKFILL_QUEUE` if customized. `--max-time=50` stops between jobs; a job already running may finish later, bounded by its 120-second timeout. The Redis slot prevents overlapping launches in that host/slot. Multiple slots and worker machines can drain the queue: atomic database leases select one job per market/period, shared market locks coordinate with live collection, a shared exchange lock serializes history workers for that exchange, and page upserts/checkpoints are transactional. CCXT's rate limiter remains enabled. The shared connection's calculated training reservation is already greater than the history timeout. The job allows additional 30-second releases while another collector holds a lock; actual request failures use the saved retry schedule described in [CLI.md](CLI.md#trademinatorbackfill-ohlcv). There is no permanent worker daemon.

A pass makes at most five 90-candle OHLCV requests, starts no new call after 45 seconds, and waits at least one minute before the next pass. A full 24-hour window of one-minute candles therefore normally needs four passes when all pages are full; one-hour candles normally need one pass for the same day. This is throughput, not a guaranteed ETA: exchange limits, sparse trading, queues and errors affect timing. Longer candle periods fetch at least one whole candle per logical window.

Inspect collection and start a due pass without waiting for the next scheduler tick:

```bash
php artisan trademinator:backfill-ohlcv --status
php artisan trademinator:backfill-ohlcv
php artisan queue:failed
```

Expected request failures and pauses are recorded in `--status` and application logs; they need not appear in `queue:failed`. A hard worker failure can also appear there. Three empty/out-of-range windows pause automatic probing. Network/rate-limit errors back off without marking history exhausted. Repeated non-network errors pause for review. The status includes the cursor and reason; see [the command reference](CLI.md#trademinatorbackfill-ohlcv) for targeted resume and immediate feature/model rebuilding.


Successful backfill windows also queue **M2 feature rebuild → fresh KNN/pattern build** on `INTELLIGENCE_QUEUE`. Keep the existing M4 intelligence cron running; no extra training cron is necessary and there is no wait until Monday. Both stages run on the intelligence worker with the derived whole-build timeout. Feature replay keeps its existing 540-second cooperative limit; each subsequent algorithm and parameter run receives its own `INTELLIGENCE_MAX_SECONDS` allowance. Preserve that worker's 512 MiB PHP ceiling and 384 MiB worker recycle threshold, shared private research/model storage, renewable ownership leases, and a queue reservation at least 300 seconds longer than the calculated job timeout. The weekly schedule remains available alongside these history-triggered builds.

Rebuilds combine pending imports per market, retain imports that arrive during training for a follow-up build, and retry after errors without deleting candles. The history worker shares M2's feature lock while inserting older rows so feature replay and dataset snapshots cannot observe history changing under an offset-based scan. `trademinator:backfill-ohlcv --status` reports both collection progress and `build_stage`, pending/trained history revisions, the most recent model ID and any `build_error`. `INTELLIGENCE_ENABLED=false` pauses these automatic rebuilds as well as weekly dispatch; pending history revisions remain available when re-enabled.


## M4.1 daily cross-exchange reevaluation

Keep the existing scheduler and `intelligence` worker above. No extra system cron entry or permanent daemon is required. At 03:45 daily, `trademinator:dispatch-lead-lag` queues integrated model rebuilds for active feeds with the same spot symbol and selected period on at least two exchanges. Each job relearns empirical timing and rebuilds the downstream KNN/pattern model. Every lead/lag parameter run and downstream learner gets its own `INTELLIGENCE_MAX_SECONDS` allowance. The job timeout and training reservation cover the complete set of enabled runs as described above. Keep the 512 MiB PHP ceiling and 384 MiB worker recycle threshold. Per-day/version generations are idempotent; failed work uses the existing retries and `queue:failed`. This adds CPU/storage work proportional to the number of eligible shared feeds, not the number of users.

Migrate before running the updated scheduler, refresh exchange metadata to seed unambiguous timezone priors, and set explicit IANA overrides where needed. `LEAD_LAG_ENABLED` and `LEAD_LAG_DAILY_REFRESH` default true; the second controls only this extra dispatcher. Both also respect `INTELLIGENCE_ENABLED`. Weekly Monday training and successful-backfill rebuilds continue and include lead/lag when enabled. Existing M4 models need one rebuild because the pattern validation protocol changed; versioned generation keys allow upgrade redispatch even within the same week. See [M4.1 upgrade and evidence contract](CLI.md#m41-cross-exchange-leadlag-and-m4-completion).

## M4.2 dashboard recording and discovery

Apply the dashboard migration and rebuild frontend assets before serving the new dashboard or running its schedules. Keep the existing scheduler and intelligence worker, and add a **separate signals worker cron**. `trademinator:dispatch-market-signals` runs every minute and queues inference on `INTELLIGENCE_SIGNALS_QUEUE` (default `signals`). When `QUEUE_CONNECTION=redis`, the signal connection defaults to `redis-signals`; its separate reservation timeout prevents the long training reservation from delaying signal redelivery after a worker crash.

```cron
# Redis deployment: the positional redis-signals connection is required for its 1200-second reservation.
* * * * * apache cd /path/to/trader-server && /usr/bin/php -d memory_limit=512M artisan trademinator:queue-work redis-signals --queue=signals --slot=1 --stop-when-empty --max-time=50 --timeout=900 --memory=384 --tries=2 >> storage/logs/signals-cron.log 2>&1
```

Match `--queue` and the positional connection to `INTELLIGENCE_SIGNALS_QUEUE` and `INTELLIGENCE_SIGNALS_CONNECTION` when customized. Keep this worker separate from training. The `redis-signals` connection uses the same Redis storage as the training connection, with `REDIS_SIGNALS_RETRY_AFTER=1200`; its queue name and worker are distinct.

Recorder jobs allow **900 seconds**, up to two attempts and a 60-second retry delay for retryable failures. A hard timeout fails the job terminally. One pending unique job per market remains locked throughout queue waiting and execution; success or terminal failure releases it for the next scheduled dispatch. The dispatcher also shares a guard with [legacy backlog recovery](CLI.md#trademinatorrecover-signal-queue) and skips safely while recovery holds it. The UI retains actual source/recording times and never invents decisions for missed intervals.

`DASHBOARD_SIGNALS_ENABLED=false` pauses dispatch and queued recorders; `INTELLIGENCE_ENABLED=false` also pauses them. Jobs recheck active subscribers and use the current selected period. Recording is shared per market, not per user. Historical journal rows remain when a user unsubscribes, but dashboard access requires their active subscription. A Server signal and a subscription never send an order; actual Client execution is Unknown until M5 reporting exists.

`trademinator:refresh-market-discovery` runs hourly at minute 10 in the scheduler background and holds a shared cache lock for up to 15 minutes. It does not use a queue worker. `DASHBOARD_DISCOVERY_ENABLED`, `COINGECKO_ENABLED` and `COINGECKO_API_KEY` control optional discovery. A default refresh makes at most 15 CoinGecko HTTP requests across all users, with the existing client timeouts; review your provider quota. Failure keeps previously cached data only while its source timestamps remain within two hours. Discovery creates no feeds, subscriptions or canonical training snapshots. The existing hourly `collect-market-context` schedule remains unchanged.

After deployment, check `php artisan schedule:list`, the signals and intelligence worker logs, `php artisan queue:failed` and the dashboard's latest recorded/source times. The scheduler's timetable is not a worker heartbeat. For an immediate observation, use the dispatch/drain examples in [CLI.md](CLI.md#trademinatordispatch-market-signals). The [M plan](M-PLAN.md) documents the user-facing acceptance contract.

## M4.3 archive export and verification

The Laravel scheduler runs `trademinator:archive-eligible-tickers` daily at **04:10** in the application timezone using `onOneServer()`, `withoutOverlapping(120)`, and `runInBackground()`. It exports and verifies complete monthly ticker shards older than `ARCHIVE_AFTER_DAYS`. It never prunes hot rows.

At **04:40** daily, `trademinator:prune-portable-archives` runs as a background Artisan command using `onOneServer()` and `withoutOverlapping(60)`. It removes expired temporary multipart transfer files and associated database metadata based on `ARCHIVE_PORTABLE_RETENTION_HOURS` (default 24); it does not delete permanent archive shards or hot ticker rows. This cleanup does not depend on an `archive` queue worker. You can run it manually using `php artisan trademinator:prune-portable-archives`.

No daemon is required. Keep the existing once-per-minute `schedule:run` cron and ensure `ARCHIVE_PATH` points to durable shared storage when multiple application nodes must read the same cold-history tier.

## Candle-level Server decision charts (October 2026)

The feature dispatcher checks for new candles every minute; the dedicated
`signals` worker above drains `trademinator:dispatch-market-signals` jobs independently
of training. Each recorder processes
up to six new completed source candles per run, records the original model and
raw Action/Outcome KNN verdicts, and never backdates its recording time.
If the model was not yet published at a source candle's close, the job records
an abstention rather than inventing a historical trading action. Signals remain
immutable. Supported repeated BUY/SELL signals are stored per candle even when
`is_change=false`; `is_change` is only for the notification timeline.

Worker settings: `RecordMarketSignal` allows 900 seconds. Its unique lock has no
waiting-time expiry and is released on success or terminal failure. Keep the
dedicated `redis-signals` worker at `--timeout=900` and its `retry_after` at least
1200 seconds. The shared Redis/Laravel cache
keeps exchange OHLCV windows for 45 seconds when recent or 10 minutes when historical.
User-specific Human Training labels and Client activity are never cached in that
shared key. No chart endpoint performs live inference.

Deploy: `php artisan migrate --force`, rebuild Vite assets with
`npm run build`, refresh configuration with `config:clear` / `config:cache`, and verify
`php artisan schedule:list`, the `features` worker, the `intelligence` worker and
the dedicated `signals` worker. Follow the targeted recovery procedure for a legacy
mixed queue before restarting its intelligence and signals consumers.
